# 비즈니스 규칙

## 제품 북극성 — 최상위 권위

Leanforge의 궁극적 목표는 **사용자가 목표와 사용자만 결정할 수 있는 선택을 제공하면, 저장소에서 도출 가능한 기술 판단·구현·검증·복구·증거 정리를 맡아 최소한의 사용자 노력으로 신뢰 가능한 변경을 완성하는 것**이다.

제품의 1차 성과는 문서 수, reviewer 수, worktree 수, mode 분류 정확도나 agent 활동량이 아니다. 1차 성과는 **Time to Trusted Change**, 즉 사용자의 최초 Prime 요청부터 승인 가능한 계약을 거쳐 검증된 실제 변경과 통합 선택을 받기까지의 총비용이다. 총비용은 wall-clock뿐 아니라 사용자 개입 시간·질문 수·읽기 부담·agent 실행 비용·재작업을 함께 포함한다.

신뢰 가능한 변경은 다음 조건을 모두 갖는다.

- 사용자가 승인할 수 있는 의도 계약이 있다.
- 승인된 의도를 구현한 실제 변경 또는 검증된 외부 결과가 있다.
- 완료 주장을 실제 명령·관찰된 출력·exit code와 필요한 runtime evidence가 뒷받침한다.
- 미처분 concern, 잔여 위험, 검증하지 못한 범위와 통합 선택이 숨지 않는다.
- durable project knowledge가 실제로 바뀐 경우에만 다음 작업을 위한 지식이 갱신된다.

정상적인 저위험 경로의 제품 목표는 사용자가 목표를 한 번 설명하고, 사용자 소유 결정만 답하고, 이해 가능한 계약을 승인한 뒤, 검증된 결과와 통합 선택을 받는 것이다. 실제 불확실성이나 위험 때문에 필요한 추가 대화는 허용하지만, Leanforge 내부 분류·스케줄링·검토 구조를 설명하거나 선택시키기 위한 질문은 허용하지 않는다.

이 절은 Prime·Run·Set·Adaptive Assurance·향후 성능 최적화의 목적과 우선순위를 규정한다. 하위 mechanism 문서가 이 절과 충돌하면 이 절이 우선한다.

## 사용자에게 귀속되는 최종 산출물

Leanforge의 사용자 산출물은 중요도 순으로 다음과 같다.

1. **검증된 실제 변경:** 구현 commit, 설정·테스트 변경, 검증된 외부 작업 또는 승인 후 통합 가능한 branch/PR.
2. **신뢰 증거와 잔여 위험 요약:** 실행한 검증, 실제 결과, 미검증 범위, concern disposition과 복구 상태.
3. **승인 가능한 의도 계약:** 무엇을 바꾸고 바꾸지 않는지, 성공 조건과 비도출 결정을 사용자가 이해할 수 있는 형태로 정리한 계약.
4. **통합 선택:** merge, PR/push, feature branch handoff 등 사용자가 소유하는 최종 선택.
5. **변경된 durable knowledge:** 장기 목표·계약·구조·운영·검증 지식이 실제로 달라진 경우에만 갱신한 프로젝트 문맥.

3-doc, reviewer, worktree, wave, mode label, shadow sidecar, load graph, semantic contract, fixture와 harness sync는 사용자 산출물이 아니라 내부 수단이다. 내부 수단은 안전성·정확성·복구 가능성 또는 총비용 중 적어도 하나를 측정 가능하게 개선해야 하며, 다른 guardrail을 악화시키면 순개선으로 인정하지 않는다.

## 제품 판정과 guardrail

새 workflow나 최적화는 다음 교집합을 만족해야 한다.

- **의도:** 사용자 소유의 중요한 결정이 숨지 않는다.
- **안전:** material risk를 더 낮은 절차로 잘못 분류하지 않는다.
- **품질:** 승인 계약과 실제 결과가 일치하고 완료 증거가 약화되지 않는다.
- **효율:** 작은 작업의 Time to Trusted Change와 agent 비용이 기존보다 나빠지지 않는다.
- **사용자 부담:** 내부 mechanism 때문에 질문·승인 단계·읽기 부담이 늘지 않는다.
- **단순성:** mode·문서·상태가 두 번째 orchestration이나 workflow DSL로 팽창하지 않는다.
- **복구:** 최적화가 불확실하거나 실패하면 검증된 Full Assurance 경로로 돌아갈 수 있다.

내부 단계를 줄였더라도 총시간·사용자 노력·재작업 또는 결함 위험이 늘면 제품 회귀다. 반대로 절차가 더 안전해 보여도 작은 변경의 총비용을 지속적으로 키우면 제품 목표를 충족하지 못한다.

## Adaptive Assurance 경계

- mode 선택은 내부 변속기다. 사용자가 `lite | standard | assurance`를 선택하거나 mode 판정을 위해 추가 질문에 답하게 해서는 안 된다.
- shadow 분류는 이미 grounded된 사실만 사용하며, 추가 repo scan·subagent·사용자 질문을 정당화하지 않는다.
- 첫 live activation은 **strict Lite와 기존 Full Assurance의 두 실행 경로**만 허용한다. `standard`는 관측·분석 label로 유지하며 독립적인 실행 topology는 별도 순효익이 입증되기 전까지 만들지 않는다.
- Lite 실행 중 새 위험이 발견되면 Standard 또는 Assurance 의미로 단조 승격하되, 실행은 기존 Full Assurance 경로로 복귀한다. 같은 cycle에서 더 낮은 경로로 다시 내리지 않는다.
- 분류 정확도만으로 activation하지 않는다. shadow overhead 비열화 없음, 사용자 부담 증가 없음, 품질 보존, 충분한 예상 절감과 명시적 복귀 경계를 함께 증명해야 한다.

## 권위와 승인

- 사용자의 목표, 기존 문서, 코드, 외부 모델 의견은 검토 재료다. 사용자가 중요한 결정을 승인하기 전에는 실행 권위가 아니며, 미확정 값을 구현 기본값으로 굳혀서는 안 된다.
- 승인 계약은 원하는 결과와 불변조건을 우선한다. 기존 코드는 현재 구현의 증거지만 승인된 제품 의도를 자동으로 재정의하지 않는다.
- 실행 중 승인 계약이 모호하거나 현재 구조와 양립하지 않으면 추측으로 진행하지 않는다. 문제와 선택지를 사용자에게 돌려보낸다.

## 역할 분리

- Prime은 의도를 정제하고 실행 가능한 계약을 만든다. 제품 파일을 구현하거나 main에 통합하지 않는다.
- Run은 승인된 계약만 실행한다. 의존 순서와 재생성 장벽을 임의로 생략하거나 추가하지 않으며, 평가할 수 없는 결과를 성공으로 간주하지 않는다.
- Set은 기존 프로젝트의 지속 가능한 운영 문맥을 정리한다. 제품 기능 구현이나 실행 계획 수행을 겸하지 않는다.
- Run TDD는 Run을 대체하지 않는다. 승인 계약과 Run의 스케줄링이 우선하며, 래퍼는 관찰 가능한 행동 변경에만 TDD 규율을 강화한다.

## 실행과 검증

- 독립적인 작업은 의존 작업이 완료되기 전에 시작할 수 있지만, 같은 쓰기 표면을 공유하는 작업은 직렬화한다.
- 위험한 작업은 격리된 branch/worktree에서 구현·검증하고, 원래 기능 branch로 반영하기 전에 diff와 명세 적합성을 확인한다.
- 완료는 실제 명령, 관찰된 출력, exit code로 증명한다. 파일 존재, 문자열 존재, symbol 존재, skipped test, 약화된 assertion은 행동 성공의 증거가 아니다.
- 동일한 전체 검증 세트가 동일한 commit에서 성공했을 때만 이전 완료 검증을 재사용한다. commit이나 검증 세트가 달라지면 다시 실행한다.
- concern은 해결, 명시적 책임 수용, 사용자 수용, 실패 승격 중 하나로 처분되어야 한다. 미결 concern을 남긴 상태로 완료하지 않는다.

## 선택적 TDD

관찰 가능한 비즈니스 규칙, 상태 전이, validation, 외부 소비자 계약을 바꾸는 작업은 실패하는 행동 테스트를 먼저 확인하고 최소 구현으로 통과시킨 뒤 정리한다. 문서, 단순 설정, formatting, 이동·이름 변경, scaffold, 제품 행동을 바꾸지 않는 build/CI 작업에는 RED 의식을 만들기 위한 테스트를 강제하지 않지만, 실제 위험을 검증하는 명령 증거는 생략하지 않는다.

## 실패와 복구

- startup·interrupted-state·archive·migration 실패는 일반 구현 실패와 같은 성공 경로로 취급하지 않는다. 각 시점의 소유자가 상태를 확인하고, 불일치가 있으면 자동 병합·삭제·덮어쓰기 대신 중단한다.
- active state나 worktree의 소유권이 불명확하면 보존이 기본이다. 성공을 만들기 위해 검증, 권한, 호환성 기준을 낮춰서는 안 된다.
